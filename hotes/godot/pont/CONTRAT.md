# Contrat du pont `wfrpPont` (v7, #2928, #2948, #3086)

Godot est un hôte du noyau, au même titre que l'hôte texte (`src/hoteTexte/`) : il envoie des gestes et lit une vue faite des lecteurs du noyau. Le pont (`pont.ts`) ne porte aucune règle ; il passe par le module commun des hôtes (`src/hote/`). Ticket : #2928. Les tests `*.hors-store.test.ts` de ce dossier vérifient ce contrat.

## Transport

- La page charge le bundle `wfrp-pont.js` (`node hotes/godot/construire.mjs --pont-seul --sortie <dossier>`), qui expose `globalThis.wfrpPont`. Le bundle lit les API de navigateur que déclare `API_DU_NAVIGATEUR` (`construire.mjs`) ; la construction l'exécute dans un contexte qui ne porte qu'elles, et la CI rougit si `demarrer` ou `vue` n'y répondent pas `ok: true`.
- `wfrpPont.appeler(methode, entree?)` est la seule fonction du pont. `methode` est le nom d'une méthode ; `entree` est une chaîne JSON qui encode un objet, ou rien (absente ou `null`) pour une méthode sans entrée. Elle rend toujours une chaîne JSON.
- La réponse vaut `{ "ok": true, … }` ou `{ "ok": false, "erreur": { "categorie", "message" } }`. `appeler` ne lève jamais.
- Une clé de l'entrée que la méthode ne lit pas se refuse.

## Erreurs

| `categorie` | Cas |
|---|---|
| `validation` | méthode inconnue (le message nomme les méthodes) ; entrée illisible, qui n'est pas un objet, ou avec une clé hors contrat ; aucune partie avant `demarrer` ; second `demarrer` ; scénario inconnu, graine non entière ; verbe inconnu (le message nomme les verbes de la fenêtre qui tient la main et les voisins de nom) ; argument de forme fausse, en trop ou manquant, id que l'état ne désigne pas ; champ de contexte qu'une offre ne lit pas ; verbe qui lève ; intention hors de l'allowlist d'un siège ; jeton inconnu ou déjà repris ; `composer` avant tout `modeles`, ou sur une base qu'il n'a pas servie ; composition de `composer` ou de `presetDeComposition` absente ou hors de son schéma (`lireComposition`, le message porte le chemin de chaque faute, `(racine)` pour la composition entière) ; `preset` de `presetDeComposition` qui n'est l'id d'aucun preset de `catalogues` (le message nomme les ids) |
| `permission` | intention d'un siège qui ne tient pas la main |
| `regle` | barre non ouverte (sa raison) ; offre que l'énumérateur ne rend pas ou qu'aucun candidat ne désigne ; offre fermée (sa raison) |
| `interne` | levée qu'aucun contrôle n'attendait |

Les trois premières catégories sont celles du module commun (`CategorieDErreur`, `src/hote/partie.ts`) ; le texte de chaque message vient de lui ou du noyau.

## Méthodes

| Méthode | Entrée | Réponse `ok: true` |
|---|---|---|
| `demarrer` | `{ scenario, graine? }` : l'id d'un scénario de test du catalogue (`testScenarios`), la graine des dés (entier, 1 par défaut) | une `Suite` : le lancement du scénario |
| `vue` | aucune | `{ vue }` |
| `jouer` | un geste : `{ offre, ctx? }` (une offre du registre et son contexte) ou `{ type, args?, siege? }` (un verbe de la partie, ses arguments, le siège qui le joue) | une `Suite` |
| `reprendre` | `{ jeton }` : le numéro d'un jeton programmé | une `Suite` : la reprise du jeton |
| `modeles` | `{ manifestes, osDesRigides }` : un objet id de modèle → manifeste et un objet id de modèle → liste d'os, ceux du listage servi (`GET modeles/`, section « Atelier 3D ») | `{ bases, glb, refus, rapport, blasons, emblemes }` : les modèles de l'atelier (`modelesDeLAtelier`, `atelier.ts`), sans partie |
| `composer` | `{ base, composition }` : l'id d'une base servie par le dernier `modeles`, une composition (section « Composition d'un personnage ») | `{ montes, manquants, rapport, gabarit, morphes }` (`composerSurLaBase`, `composition.ts`) ; refusé avant tout `modeles`, sur une base qu'il n'a pas servie, et sur une composition que `lireComposition` refuse |
| `catalogues` | aucune | les choix de chaque champ d'une composition, ses axes, et les presets avec leur composition (`cataloguesDeComposition`, surface du noyau) |
| `presetDeComposition` | `{ composition, preset? }` : une composition (section « Composition d'un personnage ») et l'id d'un preset de `catalogues` dont l'entrée reprend l'enveloppe | `{ entree, verdict }` (`presetDeComposition`, surface du noyau) ; refusé sur une composition que `lireComposition` refuse, et sur un `preset` inconnu |
| `erreursGlobales` | aucune | `{ erreurs: { message, source }[] }` : les événements `error` et `unhandledrejection` de la page depuis le dernier relevé, puis vidés ; `source` vaut `fichier:ligne`, `unhandledrejection` ou `null` |

`demarrer` ouvre la partie une seule fois par page : un second appel se refuse, et recommencer, c'est recharger la page. Un `demarrer` refusé n'ouvre rien.

Les gestes d'une fenêtre sont des verbes de la partie, joués par `jouer` : ce sont les verbes de `projection.fenetre.verbes` (`fenetreDuJeu`), réglages et flux réactif compris (`FENETRE_DU_JET`, `src/noyau/combatAuto.ts`), chacun dessiné par `vue.fenetre`. Chaque verbe de la partie et ses paramètres viennent du registre dérivé du noyau (`src/hote/verbes.generated.ts`, produit par `scripts/gen-verbes.mjs`) : ni le pont, ni ce contrat, ni le GDScript n'en nomment aucun.

## Suite

```ts
type Suite = {
  vue: Vue;
  programmes: { id: number; delai: number }[];
  journal: LigneDuJournal[];
};
```

- `programmes` : les jetons que l'appel a programmés, chacun numéroté dans l'ordre d'arrivée (`tenueDesJetons`, `src/hote/partie.ts`). Godot arme un minuteur de `delai` millisecondes, puis appelle `reprendre { jeton: id }`. Un jeton se reprend une seule fois.
- `journal` : les lignes que l'appel a écrites, `{ de: 'journal', texte }` ou `{ de: 'combat', evenement }` (`LigneDuJournal`, `src/noyau/partie.ts`).

## Vue

```ts
type Vue = {
  projection: Projection;               // projeter, src/hote/projection.ts, sans borne
  equipements: Record<string, DessinDEquipement>; // par id de combattant
  couverture: { demandes: number; absences: AbsenceDeModele[] };
  fenetre: FenetreADessiner | null;     // fenetreADessiner, src/hote/gestes.ts
  attaque: FenetreDAttaque | null;      // fenetreDAttaque, src/noyau/fenetreDAttaque.ts
  defense: FenetreDeDefense | null;     // fenetreDeDefense, src/noyau/fenetreDeDefense.ts
  panneau: PanneauDuCombat | null;      // panneauDuCombat, src/hote/ecran.ts
  cases: { zone: string; case: { x: number; y: number }; cout: number }[]; // casesAtteignables
  plateau: { w: number; h: number; infranchissables: { x: number; y: number }[] } | null; // plateauDeLaScene
  champ: { combattant: string; case: string }; // CLICS_DU_CHAMP
};
```

- `projection` est la projection commune aux hôtes, sans borne : Godot reçoit chaque liste entière. Ses champs sont des données, jamais du texte mis en forme. Elle porte notamment `fenetre` (`fenetreDuJeu` : la clé de la fenêtre qui tient la main, son propriétaire, ses verbes, l'id que ses verbes prennent en premier argument), `jets` (`jetsEnVue`), et `combat`, avec `barre` (`etatDeLaBarre` : `{ forme, raison }`), `offres` (`offresDeLActif`), `cibles` (`validTargets`), `apercu` (`battle.preview` : `{ genre, cible, case, cout }`) et `voisins` (tous les combattants, chacun avec ses États `{ id, valeur }`).
- `fenetre` est la fenêtre qui tient la main, prête à dessiner, en mots du joueur : son titre, son étape et qui tient la main (`proprietaire` : `{ genre: 'tous' }`, `{ genre: 'aucun' }` ou `{ genre: 'porteur', nom }`, `nom` à `null` quand l'état ne nomme pas le porteur ; Godot n'en dit que le nom), son corps en lignes (`corpsDeLaFenetre` : qui agit contre qui, les jets à jeter ou tombés, le DR net, l'issue), et un geste par verbe de `projection.fenetre.verbes`, dans le même ordre. Un geste porte son libellé, chacun de ses arguments (posé par la fenêtre, ou à saisir en choix, nombre, texte, objet ou JSON, avec ses valeurs nommées, ses bornes et sa valeur courante), son rendu (`bouton`, `choix`, `liste`, `formulaire` ; un argument requis, ou optionnel à valeurs nommées, est à dire), l'argument d'un `choix` ou d'une `liste` (`aChoisir`), `attendu` (le geste que la politique de la fenêtre joue maintenant) et `ouvert` (faux pour un réglage que la fenêtre lue qui le règle — attaque, Défense, butin, opération — ne nomme pas maintenant). Godot dessine chaque geste ouvert d'après son rendu ; aucun verbe n'est rendu par une liste écrite à la main.
- `attaque` et `defense` sont les fenêtres d'attaque et de la Défense en données, `null` hors de leur attente.
- `panneau` est le panneau du combat en mots du joueur : le round et le tour, la fiche de l'actif, la raison d'une barre fermée (`null` quand une fenêtre tient la main), ce que l'aperçu du premier clic coûte, la fin du combat, le titre du journal et le libellé de chaque offre par son id ; `null` hors combat.
- `cases` liste les cases que le champ peint au tour de l'actif (`porteesDuTour`), et rien hors de ce tour.
- `plateau` est le plateau de la scène (`plateauDeLaScene`, `src/noyau/monde/scene.ts`) : ses dimensions et les cases que nul ne franchit à pied ; `null` sans scène.
- `champ` nomme le verbe du clic du champ qui désigne un combattant, et celui qui désigne une case.

## Équipement et couverture des modèles

Chaque combattant (`combat.actif` et `combat.voisins.liste`) porte `equipement`, le résultat de `equipementDessine` : `weapons`, `rangees`, `armour`, `shield?` et `cape?`. Les armes portent les `candidats` ordonnés. Seules les armes tenues (`weapons`) portent une `hand` obligatoire (`main` ou `off`) ; les armes rangées n'ont pas de main. `equipDe` attribue les mains une seule fois : les mains explicites du loadout sont réservées avant les armes sans main du statbloc, qui prennent `main` puis `off` ; un bouclier demande `off`. Les attaques naturelles ne réservent aucune main. Une arme à deux mains réserve les deux mains et reste un seul objet, attaché à sa main directrice. Le surplus graphique est publié dans `rangees`, sans modifier les armes persistées ni leurs règles de combat. L'ordre relatif des armes sources est conservé dans chaque liste publiée ; `armePrincipale` désigne la première arme non-bouclier, naturelle comprise. L'appel isolé `armeDeDessin` passe par cette même attribution avec une seule arme. Le bouclier est déjà une arme tenue et `shield` en reprend les candidats. `cape` est un booléen, les pièces d'armure portent une matière ; ces deux champs ne déclarent pas de candidats de modèle.

`equipements[id]` contient `tenues` et `rangees` : chacune est une liste `{ arme, modele, palette }`, sans les armes naturelles dessinées par le corps. `arme` est la projection du noyau. `palette` est la palette résolue de `arme.teinte` par `findTeinteById`, lecteur public du noyau, ou `null` sans teinte. Les instances conservent uniquement l'id stable de teinte ; Godot ne lit aucun catalogue. `modele` est `null` si aucun candidat n’a de modèle ; sinon `{ apparence, composants: { modele, composant, pieces }[] }`, avec le premier id compatible dans l’ordre publié. Pour une arme tenue, le pont choisit le premier composant dont `montage.composants[id].prise` correspond à `arme.hand` ; pour une arme rangée, le premier qui déclare un `rangement`. Toutes les pièces de ce composant forment l’objet publié. Si un candidat n’a aucun composant compatible, le candidat suivant est essayé ; si aucun ne convient, `modele` vaut `null` et l’absence porte la liste entière des candidats. Godot ne départage aucune alternative de modèle ni de main.

L’index est dérivé au build Vite des `components.<id>.apparence` et des pièces de chaque manifeste sous `projet/modeles/*.manifeste.json`. Aucun index de modèles n’est commité. Les composants corporels (`apparence: null`) et les composants sans pièce ne sont pas des modèles d’objet disponibles.

`couverture` est le rapport de la vue courante, recalculé à chaque appel : `demandes` compte les objets tenus ou rangés à dessiner ; chaque absence porte `{ porteur, emplacement: 'tenues' | 'rangees', position, candidats }`. Le bouclier est compté une fois, parmi les armes tenues. Une absence totale reste publiée, avec `modele: null` et tous les candidats demandés.

## Montage des pièces dans Godot

Chaque manifeste déclare `montage.attaches` (`main`, `off`, `dos`, `ceinture`) : pour chaque attache, un `os` du skin, une `position` en mètres et une `rotation` en radians, deux vecteurs à trois composantes finies. `montage.composants` associe les composants d’armes à une `prise` (`main` ou `off`), un `rangement` (`dos` ou `ceinture`) et des `matieres: { cle, piece, surface }[]`. `cle` appartient au vocabulaire de palette du noyau ; `piece` nomme un nœud de ce composant ; `surface` est l'indice de primitive glTF, entier positif ou nul, avec un matériau existant. Deux clés ne peuvent pas teinter la même surface. Ce montage est requis au parse et contrôlé contre le GLB par la validation de Release. Les pièces sont rigides sans skin, directement sous l’os de leur prise déclarée.

Godot applique chaque clé présente dans la palette aux surfaces déclarées, par un `BaseMaterial3D` dupliqué et un `surface_override_material` propre à la pièce montée. La couleur d'albédo multiplie la texture conservée ; ni le mesh ni son matériau partagé ne sont modifiés. Les sept pièces d'arme de `Knight.glb` n'ont qu'une surface, matériau `knight_texture` : elle reçoit `metal`. Cet atlas ne fournit pas de surfaces séparées pour `cuir` et `accent`. Le Skeleton n'a pas de pièce d'arme déclarée et monte celles des modèles donneurs. Les pièces d'armure du porteur ne sont pas sélectionnées ni teintées depuis `armour[]` par cet hôte.

Le plateau transmet `equipements[id]` au combattant depuis la vue reçue. Le modèle du porteur vient du manifeste de son camp. Les pièces d’armes de ce modèle, désignées par `montage.composants`, sont masquées ; leurs remplaçantes sont les seules pièces nommées par `modele.composants[].pieces`, chargées depuis les modèles donneurs publiés. Pour une arme tenue, la prise publiée doit être compatible avec le portage de son composant. Pour une arme rangée, la prise ne contraint pas le montage ; son rangement déclaré désigne l’attache. Un `modele: null` ne produit aucun nœud ; son absence reste dans `couverture`. Un composant incompatible avec la prise publiée est refusé avec `prise-incompatible`, sans sélection ni repli supplémentaire dans Godot.

La recette native `projet/recettes/equipement.gd` reçoit une vue JSON figée par `figer-recette-equipement.mjs`. Elle contrôle les nœuds montés et leurs os, l’absence de skin des pièces donneuses, le masquage des armes du porteur et les absences de modèles, sans serveur ni navigateur. Son objet de campagne à plusieurs formes traverse `Partie.lancer`, `etat.campaignNarratif` et la projection du pont ; la recette contrôle son montage à partir des candidats de son apparence donnée. Son objet teinté contrôle la couleur du matériau local contre la palette publiée ; l'autre instance du même modèle reste vivante et son matériau est contrôlé intact après tous les montages.

## Atelier 3D

L'atelier dessine les bases et leurs éléments d'après la réponse de `modeles`, jamais en relisant les manifestes lui-même. Le pck exporté est figé : l'atelier tire les modèles par HTTP, à côté de `index.html`, et un GLB réexporté se recharge à chaud. Le serveur de l'export (`hotes/godot/servir.mjs`) sert :

- `GET modeles/` : le listage, `{ manifestes: Record<id, manifeste>, osDesRigides: Record<id, string[]>, erreurs: string[] }`, relu à chaque appel, en `Cache-Control: no-store`. `manifestes` ne porte que les manifestes que `verdictsDesModeles` (`asset/modeles.ts`, la validation de `recupererModeles`) accepte contre leur GLB. `osDesRigides` porte, pour chaque manifeste de `manifestes`, les os qui portent ses meshes rigides : les `os` sans doublon des `meshes` sans skin (`lireGlb`, `asset/glb.ts`), liste vide pour un modèle dont aucun mesh non skinné ne pend à un os d'un skin. `erreurs` porte, une ligne chacun, le manifeste illisible, le GLB illisible, le refus d'un manifeste et le dossier des modèles illisible. Godot passe `manifestes` et `osDesRigides` tels quels à `modeles`, qui ne les revalide pas : la validation et la lecture des os lisent le GLB, que seul le serveur détient.
- `GET modeles/<fichier>` : chaque fichier du dossier des modèles (manifeste, GLB), servi en `Cache-Control: no-store`. Un chemin hors du dossier ou qui ne s'ouvre pas en fichier reçoit 404.
- Une URI malformée reçoit 400. Le serveur continue après toute requête défaillante.

La réponse de `modeles` :

```ts
type ModelesDeLAtelier = {
  bases: { id: string; empreinte: string; points: PointDAccroche[]; lignes: LigneDePiece[]; marche: { clip: string; vitesse: number } }[];
  glb: Record<string, string>;
  refus: string[];
  rapport: string[];
  blasons: Record<string, string[]>;
  emblemes: { id: string; label: string; svg: string }[];
};
type PointDAccroche = { id: string; genre: 'emplacement' | 'prise'; attache: { os: string; position: [number, number, number]; rotation: [number, number, number] }; elements: string[] };
type LigneDePiece = { sorte: 'tete' | 'coiffure'; choix: ChoixDeLigne[] } | ({ sorte: 'piece' | 'emplacement' } & ChoixDeLigne);
type ChoixDeLigne = { id: string; label: string; elements: string[] };
```

- `bases` : les bases de l'index (base, clé) → élément (`indexerModeles`, `asset/modeles.ts`). Les `points` d'une base listent ses `emplacements`, puis ses `prises`. À chaque point vont les ids des éléments de cette base liés en `liaison.mode === 'rigide'` dont `osDesRigides` contient `attache.os` du point (`.claude/skills/creer-un-personnage-3d/references/procedure.md`, rigide tenu ; `asset/evaluateur/evaluer.ts`, `monter` ; `asset/montage.ts`, `attache-incompatible`). Un rigide dont aucun mesh ne pend à un os (décor, véhicule, mesh à la racine) n'a aucun point ni ligne ; un élément lié au `squelette` ou en `surface` n'a aucun point. Les `lignes` d'une base (#3086, D3) sont tirées de la garde-robe (`src/data/garde-robe.json`, `gardeRobe` et `emplacementDePiece` de la surface du noyau), dans son ordre : le sélecteur `tete`, dont chaque `choix` est une entrée `kind: 'tete'` ; le sélecteur `coiffure`, dont chaque `choix` est une entrée `kind: 'coiffure'` ; une bascule `piece` par entrée `kind: 'piece'` de `categorie` `vetement` ou `armure` ; une liste `emplacement` par entrée `kind: 'emplacement'` que nomme l'`emplacement` d'une pièce d'accessoire. `id` est celui de l'entrée, `label` son libellé. `elements` liste les éléments de la base liés au `squelette` ou en `surface` dont la clé vaut `id` : `cle.tete`, `cle.coiffure`, `cle.piece`, ou, pour une ligne `emplacement`, l'emplacement de la pièce `cle.piece` (`emplacementDePiece`). Une liste `elements` vide est un « manquant ». Un élément lié au `squelette` ou en `surface` va à une ligne au plus ; un accessoire `rigide` va aux points, jamais à une ligne. `empreinte` vaut `glb.sha256` de la base. `marche` vaut `marcheDeLaBase(manifeste)` (`asset/gabarit.ts`, « Gabarit d'une base ») : le clip de marche de la base et sa vitesse au sol en m/s ; une base dont la marche est refusée n'est pas servie, et son refus `[marche-ambigue] <base> : <détail>` rejoint `refus`, les autres bases restant servies.
- `glb` : le fichier, sous `modeles/`, de chaque base et de chaque élément servi, à un point ou à une ligne (`fichiersDuModele(id).glb`).
- `refus` : ceux de l'index (`[base-absente]`, `[cle-en-doublon]`, `[base-en-doublon]`, `[forme]`), puis ceux des bases à marche ambiguë (`[marche-ambigue]`). Un manifeste qui n'est pas du schéma 3 est ignoré. Un refus de l'index bloque aussi l'import et la Release (`asset/importer.ts`, `asset/release.ts` `modelesEpingles`).
- `rapport` : le rapport de l'index, qui ne bloque ni l'import ni la Release : `[emplacement-non-offert] <élément> : …` pour un accessoire dont l'emplacement de sa pièce n'est offert ni par sa base ni par un vêtement ou une armure de la même base (`emplacementsNonOfferts`, `asset/element.ts`). Cet élément n'est servi ni à un point ni à une ligne. L'import (`hotes/godot/importer.mjs`) imprime le même rapport, sans bloquer.
- `blasons` : pour chaque élément servi, à un point ou à une ligne, quelle que soit sa liaison, et pour eux seuls, les `nom` de ses `surfaces` qui portent `blason: true` (`asset/element.ts`), dans l'ordre du manifeste ; liste vide pour un élément sans surface `blason`. Le `nom` d'une surface est celui d'un matériau du GLB (`surface-absente`), dont chaque primitive porte `TEXCOORD_0` (`uv-absente`).
- `emblemes` : les entrées `kind: 'embleme'` de la garde-robe (`src/data/garde-robe.json`, `gardeRobe` de la surface du noyau), chacune réduite à `id`, `label` et `svg`. `svg` est un document SVG complet, couleurs comprises, à `viewBox` carré dont `width` et `height`, s'ils sont posés, sont égaux, chacun valant à défaut le côté du `viewBox` (une longueur sans unité vaut des `px`), puisque `Image.load_svg_from_string` les retient comme taille intrinsèque ; refusé au parse sinon (`schemas/defs/garde-robe.ts`, `refusDeSvg`). Le pont étant un bundle qui gèle `src/data`, l'emblème atteint Godot par cette réponse, sans fichier servi.

Un emplacement de montage est un point ou une ligne de pièce. Le panneau dessine chaque point, puis chaque ligne de `lignes` (#3086, D3), dans leur ordre : un point, son id puis « vide » et un bouton par élément (son id), bascules d'un même groupe, ou « aucun élément » ; le sélecteur d'une ligne `tete` ou `coiffure`, sa `sorte` puis « vide » et un bouton par choix dont `elements` n'est pas vide (son `label`), bascules d'un même groupe, puis, sous sa rangée, chaque choix vide disant « <label> : manquant », un par ligne, et ni « vide » ni bouton si aucun choix n'a d'élément ; une ligne `piece`, une bascule seule (son `label`) qui monte l'élément de la pièce ou le démonte s'il l'est, ou « <label> : manquant » ; une ligne `emplacement`, son `label` puis « vide » et un bouton par élément (son id), bascules d'un même groupe, ou « manquant ». L'élément d'un choix de sélecteur ou d'une pièce est unique, la clé (base, clé) étant unique à l'index. Le panneau a deux onglets, deux bascules d'un même groupe en tête : « Montage », montré à l'ouverture, et « Composition » ; chacun a son défilement, jamais imbriqué. « Montage » porte l'état, le `rapport` de `modeles` s'il n'est pas vide, les bases, les outils, les points et les lignes, qui partagent son défilement, puis les clips et le lecteur.

« Composition » porte la composition courante (section « Composition d'un personnage »), que Godot tient, vide à l'ouverture : un bouton par preset de `catalogues` (son `label`), qui la remplace par sa `composition` ; puis une rangée par entrée de `catalogues().axes`, dans leur ordre, son `label` en tête. Un axe `ref` ou `valeur` est un sélecteur (`cle` `"axe/<champ>"`) : « aucun », puis les choix de sa `liste` de `catalogues`, chacun par son `label` ; il pose l'id choisi dans son `champ` (`{ id }` pour `ref`, l'id nu pour `valeur`) ou retire le champ sous « aucun ». Un axe `plage` est une glissière bornée par `min` et `max`, au pas de 0,05, suivie d'un bouton « neutre » (`cle` `"axe/<champ>/neutre"`) ; elle pose sa valeur dans son `champ`, « neutre » retire le champ, et sans champ elle montre `neutre`. Godot ne nomme aucun axe ni aucune liste. Chaque sélecteur et chaque glissière montre le champ de la composition courante. Un preset appliqué ou un axe changé appelle `composer` sur la base posée : chaque emplacement monte l'élément que `montes` lui donne (le premier non nul quand plusieurs entrées visent le même emplacement) et démonte les autres, au montage décrit ci-dessous ; `gabarit` et `morphes` se posent (section « Gabarit d'une base »), le squelette remis à sa pose de repos puis le clip engagé reposé à son instant. Une composition que `composer` refuse, `{}` compris (erreur `validation`, section « Composition d'un personnage »), ne compose rien : chaque emplacement est démonté, ni gabarit ni morphe ne reste, et « composition refusée : » suivi du message de l'erreur, qui porte le chemin de chaque faute, prend la place des manquants ; le message va aussi aux `erreurs`. Un os de `gabarit` que la base n'a pas donne `os-absent : <os>` aux `erreurs` du gabarit posé, que chaque pose du gabarit remplace : à chaque composition, à chaque « Recharger » et à chaque changement de base. Un preset appliqué, un axe changé et « Copier » sont des gestes de composition : les `erreurs` de chacun (refus, montage qu'il demande) remplacent celles du précédent, et chaque composition efface le texte de « Copier ». Les `morphes` se reposent à chaque élément monté et à chaque « Recharger », qui garde la composition composée ; changer de base l'efface. Sous les axes, « manquants : » puis une ligne par entrée de `manquants`, son `label` suivi de `par.label`, le libellé de ce qui l'apporte, ou « manquants : aucun » ; puis le `rapport` de `composer` s'il n'est pas vide. « Copier » rend par `presetDeComposition` la composition courante, avec `preset`, l'id du dernier preset appliqué, s'il y en a un ; il affiche son verdict (« verdict : valide », ou une ligne `chemin : message` par faute) puis l'entrée, et copie l'entrée au presse-papiers (`DisplayServer.clipboard_set`) ; refusé (erreur `validation`), il affiche « composition refusée : » suivi du message à la place du verdict, sans entrée ni copie. Godot n'écrit aucun champ de l'enveloppe.

Au montage d'un élément, à un point ou à une ligne, Godot instancie son GLB et monte chacun de ses meshes (#3086, D4) : un mesh rigide passe sous un os sous l'os de la base de même nom, à sa position locale, comme l'évaluateur (`asset/evaluateur/evaluer.ts`, `monter`) ; un mesh skinné passe sous le `Skeleton3D` de la base, qui devient son `skeleton`, et son skin se lie par NOM d'os : le GLB se charge avec le drapeau `GLTFDocument.IMPORT_FLAG_USE_NAMED_SKIN_BINDS` d'`append_from_buffer`, qui donne à chaque liaison le nom du nœud de son joint, sans indice d'os (`Skin.add_named_bind` ; `modules/gltf/gltf_document.cpp` `_create_skins`, Godot 4.7-stable), et le squelette de la base résout une liaison nommée par le nom de ses os, avant tout indice (`scene/3d/skeleton_3d.cpp`, `NOTIFICATION_UPDATE_SKELETON`, Godot 4.7-stable), quels que soient l'ordre des joints et celui des nœuds du GLB de l'élément. Sans ce drapeau, chaque liaison porterait l'indice de son os dans le squelette du GLB de l'élément, que l'import range par indice de nœud (`modules/gltf/skin_tool.cpp` `_create_skeletons`), et que rien ne relie aux os de la base. Un mesh à la racine, ni pendu à un os ni skinné, n'est pas monté. Chaque os qu'un mesh nomme (l'os de son attache, ou le nom d'une liaison de son skin) et que la base n'a pas ajoute `os-absent : <os>` aux `erreurs`, et l'élément n'est pas monté ; un élément sans mesh à monter ajoute `element-sans-piece : <element>` et n'est pas monté.

Un élément monté dont `blasons` n'est pas vide offre, sous la rangée de son emplacement, une rangée « emblème » : « vide » puis un bouton par entrée d'`emblemes` (son `label`), bascules d'un même groupe, chacune de `cle` `"<emplacement>/embleme/<id>"` (`"<emplacement>/embleme/vide"` pour « vide »), `<emplacement>` valant l'id du point ou `ligne/<ligne>`. Choisir un emblème le pose sur chaque surface d'un mesh monté, rigide ou skinné, dont le matériau actif porte (par `resource_name`) un nom de `blasons[element]` : `MontageDEquipement.materiau_local` (`projet/scripts/montage_equipement.gd`, le duplicata que `_teinter` pose aussi) en fait un matériau propre à la pièce, dont la couche *detail* reçoit l'emblème (`detail_enabled`, `detail_albedo`, `detail_uv_layer` UV1, `detail_blend_mode` mix) ; ni le mesh ni le matériau partagé ne changent. Avant chaque pose, chaque surface du mesh rend son override : « vide » laisse les surfaces au matériau du GLB. Le SVG se rastérise par `Image.load_svg_from_string` à 512 px de large (échelle 512 / largeur intrinsèque), mipmaps générées ; un SVG illisible ajoute `embleme-illisible : <id> (<erreur>)` aux `erreurs` publiées et ne pose rien. Un emblème qui ne se pose sur aucune surface (aucun matériau actif ne porte un nom de `blasons[element]`, ou aucun n'est un `BaseMaterial3D`) ajoute `blason-sans-surface : <element>` aux `erreurs` et n'est pas posé : `emblemes` n'en porte rien. Chaque pose réécrit `%Etat`, erreurs comprises, au « Recharger » aussi. Le carré UV [0,1]² de la surface porteuse est le cadre de l'emblème (`.claude/skills/creer-un-personnage-3d/references/procedure.md`).

Démonter un emplacement (ou y monter un autre élément) efface son emblème et sa rangée. « Recharger » remonte les éléments montés, rigides et skinnés, que leurs emplacements offrent encore sous l'emblème qu'ils portaient, s'il est toujours offert (« vide » sinon) ; changer de base n'en garde aucun.

La marche (`projet/scripts/marche.gd`, `MarcheDeLAtelier`) : les actions `avant`, `arriere`, `gauche` et `droite` (`project.godot`, `[input]`) portent chacune une touche par `physical_keycode`, W, S, A et D du clavier QWERTY américain (Z, S, Q et D d'un AZERTY), et une flèche. Tant qu'une est tenue et que son appui a atteint `_input` de la marche, la racine du modèle avance sur le sol dans la direction de ces actions (`MiseEnPage.entree_de_marche`), tournée par le lacet de la caméra, le modèle face à cette direction (son avant en +Z), à `marche.vitesse` m/s multipliée par `speed_scale` du lecteur, et l'atelier joue `marche.clip` à son lecteur comme au clic de son bouton ; relâchée, le clip reste engagé, en pause à son début, et le squelette revient à sa pose de repos (`Skeleton3D.reset_bone_poses`). Ces touches ne déplacent pas le focus du panneau ; une touche que l'interface prend avant la scène ne fait pas marcher : la liste ouverte d'un `OptionButton`, fenêtre incrustée qui a le focus, la reçoit avant tout `_input` (« Using InputEvent », « How does it work? », Godot 4.7). La caméra orbite autour de la racine, qu'elle suit : glisser au bouton droit tourne son lacet et son tangage (borné), la molette l'approche ou l'éloigne. La caméra de la scène cadre le corps neutre ; chaque gabarit posé, une fois mesuré au repos (`GabaritDuSquelette.mesures`), met l'orbite à l'échelle du sommet de ses os rapporté à celui du corps neutre (`MiseEnPage.echelle_de_cadrage`), le zoom repris de là ; sans gabarit, elle revient à la caméra de la scène. Un cran de molette sur un contrôle de l'interface (`Viewport.gui_get_hovered_control`) ne zoome jamais, même quand le défilement du panneau, en bout de course, le laisse passer.

### Gabarit d'une base

Godot ne calcule aucun facteur : il reçoit des nombres par nom d'os et par nom de shape key, calculés une fois en TS (`asset/gabarit.ts`) sur les facteurs de `gabaritResolu` (`GabaritResolu`, surface du noyau). L'évaluateur les applique à la pose de repos de la base (`appliquerGabarit`, `asset/evaluateur/gabarit.ts`) ; Godot les applique à la pose de chaque image, après le clip, par un `SkeletonModifier3D` enfant du squelette (`projet/scripts/gabarit_du_squelette.gd`, `GabaritDuSquelette`), ce qui revient au même au repos et garde les proportions pendant un clip, dont les pistes réécrivent la pose : le moteur joue un modificateur après l'`AnimationMixer` et restaure la pose non modifiée après le skinning (`Skeleton3D`, `NOTIFICATION_UPDATE_SKELETON`), sans cumul d'une image à l'autre. L'os `racine.os` voit son échelle de pose multipliée par `echelle`, et chaque os enfant la composante Y de sa position de pose :

- `poseDuGabarit(manifeste, facteurs)` → `{ racine: { os, echelle }, enfantsDe: Record<os, facteur>, echellesDesOs: Record<os, [x, y, z]>, pieds: os[] }`, `manifeste` étant le manifeste de base, dont elle lit `gabarit` (la table) et `appuis.pieds`. L'os `racine.os` reçoit l'échelle uniforme `echelle` (`sl`). Pour chaque os de `enfantsDe`, chaque os enfant direct du squelette voit la composante Y de sa position de repos locale multipliée par le facteur (`legs`, `arms` ou `head` selon l'unique clé de la table qui liste l'os) ; X et Z, rotations et échelles des enfants ne changent pas. La table nomme les os parents, l'hôte lit leurs enfants dans le squelette. `pieds` vaut `appuis.pieds`. À chaque pose, le repos comme chaque instant d'un clip, l'hôte : (1) lit la hauteur monde du plus bas des os de `pieds` dans la pose jouée sans gabarit ; (2) pose le gabarit, l'échelle de la racine et la composante Y des enfants composées avec cette pose ; (3) translate verticalement la racine `racine.os`, dans le repère de son parent, d'autant qu'il faut pour ramener le plus bas des os de `pieds` à la hauteur lue en (1). Les pieds gardent le contact que la pose jouée leur donne, quel que soit le gabarit ; aucune translation n'est stockée d'une pose à l'autre. L'évaluateur le fait par un seul chemin, au repos dans `appliquerGabarit` comme à chaque instant dans `reposerGabarit` ; Godot dans `GabaritDuSquelette`. Pendant un clip, le gabarit se compose avec la pose jouée, il ne la remplace pas : l'échelle de la racine vaut l'échelle animée multipliée par `echelle`, la composante Y d'un os enfant la valeur animée multipliée par son facteur, la position de la racine la position animée plus la translation de l'instant ; une valeur que le clip n'anime pas part de la pose sans gabarit. Godot le fait dans `_poser_sur`, l'évaluateur après chaque instant joué (`reposerGabarit`, appelé par `echantillonner`).
La table est disjointe entre `legs`, `arms` et `head` : le schéma refuse un os sous deux clés, en nommant l'os et les deux clés. Le champ `racine` ne participe pas à cette disjonction. `echellesDesOs` donne, pour chaque os listé, S_b = `(1, f, 1)` sous `legs` et `arms`, `(f, f, f)` sous `head`. Les hôtes disposent ainsi des multiplicateurs du décalage local d'un emplacement ou d'une prise sur cet os ; ce champ ne modifie pas l'échelle du squelette.

`poserEnfantsDuGabarit(enfants)` (`asset/evaluateur/gabarit.ts`) porte l'étape commune qui multiplie le Y local des enfants. `reposerGabarit` l'appelle. `bindsAuGabarit(squelette, pose)` l'emploie au repos sans gabarit et rend tous les binds `Bind′_b = inv(G′_b)·G_b·Bind_b` : G est la matrice monde de repos sans gabarit, G′ la même après cette seule étape, hors `sl` et hors translation de la racine. L'appel attend le squelette au repos sans gabarit ; il rend les positions et matrices à leur état d'entrée et ne modifie pas ses binds. La pose des binds rendus appartient à l'intégration de chaque hôte.

- `poidsDuGabarit(facteurs, bornes, silhouettes)` → `Record<shapeKey, poids>`. `BornesDuGabarit` porte par `legs`, `arms`, `head` les `{ min, max }` cuits par la construction, avec `min < 1 < max`. La fonction refuse les bornes invalides. `nomDeCleDuGabarit(k, sens, silhouette?)` est l'unique construction des noms : `gabarit_<k>_<sens>` et `gabarit_<k>_<sens>_<silhouette>`, `sens` valant `moins` ou `plus`. Pour le sens de `f_k − 1`, le poids vaut `max(0, (f_k − 1)/(f_sens − 1))`, avec `f_moins = min` et `f_plus = max` ; l'autre sens vaut 0. Au neutre les deux valent 0. Le poids n'est pas plafonné à 1. Chaque clé croisée vaut ce poids multiplié par celui de la silhouette reçue, sortie de `poidsDeSilhouettes`, sans recalcul. Les poids rendus incluent les zéros. Les hôtes disposent de ces poids par nom pour la pose des shape keys.
- `poidsDeSilhouettes({ sex, build, st }, table)` → `Record<shapeKey, poids>` : `carrure_moins` et `carrure_plus` par `poidsDeCarrure`, `feminin` à 1 pour `F` et 0 sinon, `corpulence` par `build`. Chaque poids se pose par nom sur chaque mesh de la base ET de chaque élément monté qui porte une shape key de ce nom ; un mesh sans cette clé n'en reçoit rien. Évaluation d'ingénierie révisable, sans arbitrage utilisateur : le corps neutre de la base est `build` `BUILD_NEUTRE` (`src/lib/corpulence.ts`), et `corpulence`, qui n'épaissit que dans un sens, vaut 0 de `build` 0 à `BUILD_NEUTRE` puis croît linéairement jusqu'à 1 à `build` 1.
- `marcheDeLaBase(manifeste)` → `{ ok: true, clip, vitesse }`, ou le refus `{ ok: false, code: 'marche-ambigue', detail }` : le clip de marche est l'unique clé de `appuis.vitessesAuSol` du manifeste de base ; zéro ou plusieurs clés sont refusées. `vitesse` vaut `vitessesAuSol[clip]`, en m/s, mesurée sur le corps neutre ; elle ne suit pas le gabarit, dont la foulée suit `sl` et `legs`, si bien qu'hors du gabarit neutre le pied glisse à la marche : écart ouvert sur #3104 (loi de la vitesse au sol par facteur).

## Composition d'un personnage

Une composition est une entrée de `src/data/presets-de-personnage.json` sans son enveloppe, les clés de `CLES_ENVELOPPE` (`src/data/schemas/grammaire/document.ts`) : `race`, `gabarit?`, `sex`, `build?`, `tete`, `coiffure?`, `tenue?`, `pieces?`, `objets?`, `prises?`, `apparencesObjets?` (`compositionSchema`, `schemas/defs/presets-de-personnage.ts`). Une seule fonction du noyau la valide, `lireComposition` (`src/noyau/apparence/composition.ts`), au schéma du preset et à ses règles, dont « rien n'est porté deux fois » : `composer` et `presetDeComposition` la lisent ; une composition refusée, ou absente, est une erreur `validation` qui nomme le chemin de chaque faute. Ce qu'elle porte vient du noyau (`porteeDeComposition`, `src/noyau/apparence/composition.ts`), dans cet ordre : la tête, la coiffure, les pièces de l'ensemble de la tenue, les `pieces`, puis chaque objet, tenu (`prises`) puis porté (`objets`). Un objet habillé par un ensemble de la garde-robe apporte ses pièces ; sinon il porte son apparence (`apparencesObjets`, à défaut sa forme `shape`) à sa prise s'il est tenu, sinon à son `rangement` (`trappings.json`) ; sans l'un ni l'autre, il va à `rapport`, sans point.

```ts
type CompositionSurLaBase = {
  montes: { ligne: string; element: string | null }[];
  manquants: { ligne: string; champ: 'tete' | 'coiffure' | 'piece' | 'apparence'; id: string; label: string; par?: { type: 'tenue' | 'trapping'; id: string; label: string } }[];
  rapport: string[];
  gabarit: { racine: { os: string; echelle: number }; enfantsDe: Record<string, number>; pieds: string[] };
  morphes: Record<string, number>;
};
```

- `montes` : une entrée par chose portée, dans l'ordre ci-dessus. `ligne` est la clé d'emplacement du panneau (section « Écran publié »), tirée d'une seule fonction (`cleDuPanneau`, `composition.ts`) : `"ligne/tete"`, `"ligne/coiffure"`, `"ligne/piece/<id>"` d'un vêtement ou d'une armure, `"ligne/emplacement/<id>"` d'une pièce d'accessoire, ou l'id du point d'un objet tenu ou rangé, et d'une pièce d'accessoire rigide. `element` est l'élément de cet emplacement, parmi ceux que `modeles` y sert, dont la `cle` désigne la chose (`cle.tete`, `cle.coiffure`, `cle.piece`, `cle.apparence`) ; une pièce d'accessoire se cherche à sa ligne puis au point de son emplacement (accessoire rigide). `null` : aucun.
- `manquants` : les entrées de `montes` sans élément, ce qu'il reste à produire : la clé (`champ`, `id`), le libellé de la garde-robe ou de l'apparence, et `par`, la tenue ou l'objet qui apporte la chose (son ensemble, ou l'objet dont elle est l'apparence), avec `label`, le libellé de son ensemble, à défaut celui de l'objet.
- `gabarit` : `poseDuGabarit` (section « Gabarit d'une base ») sur les facteurs de `gabaritResolu` de la composition (son `gabarit`, à défaut celui de sa race et sa surcharge, `raceAppearance.json`).
- `morphes` : `poidsDeSilhouettes` sur `sex`, `build` (absent : `BUILD_NEUTRE`) et le `st` de ces facteurs.
- Aucune couleur n'est publiée : la teinte d'un objet attend #2966 (évaluation d'ingénierie, 2026-10-31).

`catalogues` rend `{ race, gabarit, sex, tete, coiffure, tenue, pieces, objets, prises, axes, presets }`, chacun hors `axes` et `presets` une liste `{ id, label }` : l'id se stocke, le libellé s'affiche. Chaque champ se tire de son nœud au schéma du preset (`noeudDuChamp`) : un enum nommé, ou celui de la clé d'un record, par `optionsDuNoeud` (`sex` ; `prises`, les mains, dont l'objet se choisit dans `objets`) ; sinon sa feuille `idDe`, dont les entrées admises par sa sous-liste viennent du dataset de son espace, dans l'ordre de la donnée. `presets` liste les entrées de `presets-de-personnage.json` en `{ id, label, composition }` : `composition` est l'entrée sans son enveloppe, la forme que `composer` prend. `axes` liste les axes d'une composition, dans leur ordre (race, gabarit, sexe, corpulence, tête, coiffure, tenue), une seule déclaration au noyau (`AXES`, `composition.ts`) :

```ts
type Axe = { champ: string; label: string } & (
  | { forme: 'ref' | 'valeur'; liste: string }
  | { forme: 'plage'; min: number; max: number; neutre: number }
);
```

`label` est le libellé de la méta du champ au schéma du preset (`meta`, `schemas/defs/presets-de-personnage.ts`). `forme` se lit au nœud du champ : `ref` quand son `id` est une feuille `idDe` (le champ porte `{ id }`), `valeur` pour un enum nommé (le champ porte l'id nu), `plage` pour un nombre borné ; `liste` est la clé de `catalogues` qui donne ses choix, `min` et `max` les bornes du nœud, `neutre` la valeur que vaut le champ absent (`build` : `BUILD_NEUTRE`, `src/lib/corpulence.ts`), que porte toute `plage` : un nombre borné sans neutre dans `NEUTRES` (`composition.ts`) fait échouer `catalogues`. Godot tient la composition courante : appliquer un preset la remplace, changer un axe la modifie, et l'une ou l'autre se recompose par `composer` ; `presetDeComposition` sérialise cette même forme, l'enveloppe ajoutée par le noyau.

`presetDeComposition` rend `{ entree: string, verdict: { chemin: (string | number)[]; message: string }[] }` : `entree` est l'entrée au format du fichier (`serializeDataset`), clés dans l'ordre du schéma quand elle est valide : le `type` de la collection, lu au schéma, l'enveloppe entière du preset `preset` s'il est donné (ses clés de `CLES_ENVELOPPE`, hors `type`), puis la composition. `verdict` porte les fautes du schéma de la collection (`validateDocument`), chemin dans l'entrée, vide si elle est valide : sa composition étant validée d'abord, ce sont celles de l'enveloppe, `id`, `label` et `source` sans `preset`. Seule une entrée au verdict vide se copie dans le fichier.

## Écran publié

L'entrée de l'application est un menu (`scenes/Accueil.tscn`, `run/main_scene`) à deux boutons, « Combat » et « Atelier ». Arbitrage utilisateur, 2026-10-28 : « A terme le menu de l'application passera aussi par godot et il existera un bouton du menu pour aller dans l'atelier ».

Chaque vue mise en page, Godot pose `globalThis.wfrpEcran`. Chaque publication remplace l'objet.

- Au menu : `{ boutons: { texte, x, y }[] }`, le texte et le centre de chaque bouton actif.
- Au combat : `{ boutons: { texte, x, y }[], cases: Record<"x,y", [x, y]> }`, plus le point de l'écran de chaque case du plateau.
- À l'atelier : `{ boutons: { texte, x, y, cle? }[], atelier: { base: string|null, empreinte: string|null, clip: string|null, instant: number|null, duree: number|null, lecture: boolean, vitesse: number, montes: Record<point, element>, lignes: Record<ligne, element>, emblemes: Record<emplacement, emblemeId>, aides: { os: boolean, emplacements: boolean, prises: boolean }, erreurs: string[], onglet: 'montage' | 'composition', plages: Record<champ, { gauche: number, droite: number, y: number, valeur: number }>, composition: { courante: Composition, preset: string|null, montes: Monte[], manquants: Manquant[], refus: string|null, copie: string }, gabarit: { neutre?: Mesure, repos?: Mesure, image?: Mesure }, cadre: number, os: Record<os, [number, number, number]>, peaux: Record<emplacement, { centre: [number, number, number], taille: [number, number, number] }> } }`, `Mesure` valant `{ pied: number, piedSansGabarit: number, sommet: number, echelle: number }`. `composition` porte la composition courante (`{}` à l'ouverture), l'id du dernier preset appliqué, puis `montes` et `manquants` de la dernière réponse de `composer` sur la base posée (section « Composition d'un personnage »), vides avant toute composition, après un refus et après un changement de base ; `refus` est le texte affiché du refus de la composition courante (« composition refusée : » suivi du message), `null` sans refus, et `copie` le texte affiché par « Copier » à la place du verdict, vide avant tout « Copier » et après chaque composition. `erreurs` porte celles du chargement, du montage et de la page, puis celles du dernier geste de composition, puis celles du gabarit posé (section « Atelier 3D »). `cadre` est l'échelle de l'orbite de la caméra (`MarcheDeLAtelier.echelle`), 1 au corps neutre. `gabarit` porte les mesures du gabarit posé par `GabaritDuSquelette` (section « Gabarit d'une base »), vide sans gabarit et avant sa mesure : `neutre` au repos sans gabarit, `repos` au repos au gabarit, pieds au sol, et `image` sur la dernière pose modifiée, au repos comme pendant un clip ; chacune la hauteur monde de l'os de `pieds` le plus bas (`pied`), celle de l'os de `pieds` le plus bas de la même pose sans gabarit (`piedSansGabarit`), que `pied` égale (« Gabarit d'une base », étape 3), celle de l'os le plus haut (`sommet`), et l'échelle monde de `racine.os` (`echelle`). `os` porte la position monde de chaque os de la base sur la pose courante, par nom, vide sans base. `peaux` porte, sous l'id du point ou `ligne/<ligne>` de chaque emplacement monté qui porte un mesh skinné, la boîte de ses meshes skinnés posés par le moteur sur la pose courante (`MeshInstance3D.bake_mesh_from_current_skeleton_pose`, qui lit les os que le squelette a liés au skin) : son centre monde (`centre`) et sa taille dans le repère du squelette (`taille`). `plages` porte, par `champ` d'un axe `plage` dont la glissière est à l'écran, le bord gauche et le bord droit de son cadre et son milieu vertical, et la valeur de la glissière (`valeur`, le `neutre` de l'axe sans champ) : un clic sur un bord pose la borne de l'axe. `cle` est optionnelle : un bouton d'emplacement la porte, `"<point>/<element>"` ou `"<point>/vide"`, le sélecteur d'un axe `"axe/<champ>"` et le bouton « neutre » d'un axe `plage` `"axe/<champ>/neutre"`, un bouton de ligne de pièce `"ligne/<sorte>/<id>"` ou `"ligne/<sorte>/vide"` pour un sélecteur (`id` du choix), `"ligne/piece/<id>"` pour une pièce, `"ligne/emplacement/<id>/<element>"` ou `"ligne/emplacement/<id>/vide"` pour un emplacement, et un bouton d'emblème `"<emplacement>/embleme/<id>"` ou `"<emplacement>/embleme/vide"`, parce que son texte (« vide », un id d'élément, un libellé) se répète d'une ligne à l'autre ; le préfixe `ligne/` sépare une ligne d'un point de même id. `lignes` porte l'élément monté à chaque ligne de pièce, sous la clé `<ligne>` : la `sorte` d'un sélecteur (`tete`, `coiffure`), `piece/<id>` ou `emplacement/<id>` ; une ligne sous « vide » ou démontée en est absente, comme un point de `montes`. `emblemes` ne porte que les emplacements montés dont un emblème est posé, sous l'id du point ou `ligne/<ligne>` : un emplacement sous « vide » ou démonté en est absent. `duree` est la longueur du clip engagé (`null` sans clip) : chaque clip boucle, et « Image suivante » / « Image précédente » mènent à l'image voisine modulo `duree` (`MiseEnPage.image_voisine`, `projet/scripts/mise_en_page.gd`), la suivante de la dernière image étant la première.

Les recettes de `hotes/godot/recette.mjs` partent du menu et ne jouent aucun geste par le pont. Le tour complet clique « Combat », puis y lit où cliquer ; il observe la partie par `vue`. L'atelier (`--parcours atelier`) clique « Atelier », lit ses boutons et son état dans `wfrpEcran`, et sert un dossier de modèles neuf que la recette remplit par `importer.mjs --sans-publier`.
